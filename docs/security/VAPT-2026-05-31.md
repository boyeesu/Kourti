# Kourti Legal — VAPT Report

**Date:** 2026-05-31
**Type:** Full VAPT (static code audit + non-destructive live testing)
**Scope:** Backend API (Railway), Main app (Vercel), Marketing site (Vercel), Client portal
**Authorization:** Owner-authorized; live testing limited to non-destructive checks (TLS/headers, auth-bypass probes, CORS, info-disclosure). No DoS, fuzzing, brute force, or data destruction.
**Targets:**

- App: `https://app.kourti.com` (Vercel)
- Marketing: `https://kourti.com` (Vercel)
- Backend API: `https://kourti-backend-production.up.railway.app` (Railway)
- Client portal: served from app origin; API at `/api/v1/portal/*`

---

## Executive summary

The platform's **runtime security posture is strong**. Live probing of the production backend found **zero Critical/High issues**: TLS 1.3 only (legacy refused), HTTPS enforced, full Helmet header set, `X-Powered-By` suppressed, clean generic 404s with no information disclosure, JWT verification rejecting `alg:none`/forged tokens, all authenticated and portal endpoints correctly returning 401/403 unauthenticated, and CORS correctly refusing to reflect untrusted origins. Dependencies (frontend + backend production) have **no known vulnerabilities**, and `.env` files are gitignored and **never appeared in git history** (independently verified).

The findings below come almost entirely from the **static code audit** and are predominantly **defense-in-depth gaps and hardening items** rather than live-exploitable holes. The highest-value fixes: cap signed-URL expiry, verify rate-limiting is not bypassable behind Railway's proxy, move the portal refresh token off `localStorage`, and rotate/segregate the production secrets sitting in the local `.env`.

## HIGH

### H1 — Signed document download URL expiry is uncapped (~68 years possible)

**Surface:** Backend · `backend-node/src/routes/api/files.ts:329,351`
`const expiresIn = Number(req.query.expiresIn) || 3600;` — any authenticated user can request `expiresIn=2147483647`. The signed URL _is_ the credential (carries no user identity), so it grants document access long after the session ends or the account is deactivated, and is freely shareable.
**Fix:** `const expiresIn = Math.min(Number(req.query.expiresIn) || 3600, 3600);` (e.g. cap 3600 staff / 900 portal).

### H2 — Production secrets present in local `backend-node/.env` (NOT in git, but prod-pointing)

**Surface:** Backend · `backend-node/.env`
The local `.env` contains live-looking secrets and its `DATABASE_URL` points at the **production** Railway DB proxy (`hopper.proxy.rlwy.net`), alongside `JWT_SECRET`, `JWT_REFRESH_SECRET`, `OPENAI_API_KEY`, and a `sk_test_` Paystack key.
**Independently verified:** `.env` is in `.gitignore` and **never appears in git history** (`git log --all -- backend-node/.env` empty) — so this is **NOT a repository leak** (the marketing sub-audit's "committed to version control / Critical" framing is corrected here).
The residual risk is **prod-credential sprawl on developer machines**: if this file's `JWT_SECRET` equals production, anyone with local read access (or any future backup/sync/screen-share) can forge prod JWTs and reach the prod DB. (Could not confirm the exact match — pulling live secret values was outside the authorized scope.)
**Fix:** Use non-production secrets for local dev; keep prod secrets only in Railway env. If this file's secrets equal prod, **rotate** `JWT_SECRET`, `JWT_REFRESH_SECRET`, DB password, and `OPENAI_API_KEY`, and point local `DATABASE_URL` at a dev DB. Becomes **Critical** if this `.env` has ever been shared/synced.

### H3 — Rate limiting may be bypassable behind Railway's proxy (X-Forwarded-For trust) — VERIFY

**Surface:** Backend · `backend-node/src/app.ts:142` (`app.set('trust proxy', 1)`), `src/lib/rateLimit.ts`, `routes/api/public.ts`
If Express resolves `req.ip` from an attacker-suppliable position of `X-Forwarded-For` given Railway's edge behavior, per-IP limits on `/chat`, `/contact`, `/assessment`, and auth become bypassable by rotating forged IPs — enabling LLM-cost amplification and lead-spam. The live probe could **not** confirm rate-limiting behavior (no `RateLimit-*` headers observed, only 8 test requests), so this is **plausible but unverified**.
**Fix:** Verify Railway's real client IP position and configure `trust proxy` / a `keyGenerator` to read the correct (rightmost-appended) hop. Enable `standardHeaders: true` so limits are observable.

### H4 — Public chat (MARTHA) has no input-token budget; history accepted verbatim

**Surface:** Backend · `backend-node/src/routes/api/public.ts:363-374,446-451`
Up to 12×4,000-char history messages + 2,000-char message are concatenated into LLM input with no input-token cap (output capped at 700). Cost-amplification vector, compounded by H3. History array also lets a caller inject `assistant`-role turns (indirect prompt injection / KB exfil attempts).
**Fix:** Cap total `message + history` length (e.g. 6,000 chars); inject `assistant` turns server-side rather than trusting client-supplied roles; add a global concurrent-SSE ceiling and a daily token budget.

### H5 — Client portal refresh token stored in `localStorage` (XSS-extractable)

**Surface:** Frontend · `src/portal/portalApi.ts:22-49`
Portal `accessToken` + `refreshToken` live in `localStorage` (`kourti_portal_tokens`). The staff app deliberately keeps the access token in-memory and the refresh token in an httpOnly cookie (`src/lib/authClient.ts:37`); the portal does not, so any XSS or malicious 3rd-party script silently exfiltrates a long-lived refresh token.
**Fix:** Mirror the staff model — access token in memory, refresh token in an httpOnly cookie (needs backend `Set-Cookie` on `/portal/auth/refresh`). Minimum interim: `sessionStorage`.

### H6 — Client portal refresh lacks reuse detection + audit event

**Surface:** Backend · `backend-node/src/services/clientPortalAuth.ts:448-481,476`
Staff `refreshTokens` (`services/jwt.ts:944-970`) detects stolen-token reuse (bumps token_version, kills the session family) and logs a security event. The client portal's `clientRefresh` does neither — a stolen portal refresh token can be rotated indefinitely with no revocation or audit trail. Most impactful on the public-facing portal (combine with H5).
**Fix:** Port the reuse-detection + `logSecurityEvent` logic into `clientRefresh`.

### H7 — `force-change-password` does not re-verify the current password

**Surface:** Backend · `backend-node/src/routes/api/authRoutes.ts:460-491`
Behind `requireAuth` but, unlike `changePassword`, requires no current password and no check that the user is actually in a `must_change_password` state. A stolen live access token can silently replace a victim's password.
**Fix:** Gate on `profiles.must_change_password = true`, or require `currentPassword`.

### H8 — `agents.ts` admin check uses divergent `profiles.role` column

**Surface:** Backend · `backend-node/src/routes/api/agents.ts:24-32`
Authorization for agent-job creation reads free-text `profiles.role` against `['admin','owner','partner']` instead of the canonical `user_role_assignments` model used elsewhere. Inconsistent — anyone whose `profiles.role` string happens to match gains access regardless of real capability assignment; a real superadmin via `user_role_assignments` with a non-matching `profiles.role` is denied.
**Fix:** Replace with a `user_role_assignments`/capability query consistent with the rest of the codebase.

## MEDIUM

### M1 — Multi-tenant `organization_id` scope missing on portal case/message queries (defense-in-depth)

**Surface:** Backend · `portal.ts:439-463` (case), `portal.ts:590-605` (messages)
`assertClientCaseAccess` correctly anchors access, but the subsequent SELECT/UPDATE on `cases` / `case_client_messages` omit `AND organization_id = …` that the staff side (`clientPortal.ts:1204`) includes. Not currently exploitable (case UUIDs are globally unique), but a DB restore/UUID reuse or a future access-check regression would remove the only backstop.
**Fix:** Thread the `organizationId` already returned by `assertClientCaseAccess` into all subsequent queries.

### M2 — `KB_SYNC_SECRET` compared with non-constant-time `!==` (timing oracle)

**Surface:** Backend · `public.ts:507-508`
Public `POST /kb/sync` token compared with `!==`. Theoretical timing recovery → KB poisoning of MARTHA. (Network timing attacks are hard, hence Medium.)
**Fix:** `crypto.timingSafeEqual` after length check.

### M3 — `Access-Control-Allow-Credentials: true` emitted unconditionally

**Surface:** Backend (live-confirmed by both probes) · CORS middleware
Sent on every response incl. untrusted origins. **Not exploitable** — the server never reflects `Access-Control-Allow-Origin` for untrusted origins (allowlist works), so browsers block credentialed reads. Cosmetic, but tighten so `credentials:true` only pairs with an allowlisted origin.
**Fix:** Only emit the credentials flag for allowlisted origins; consider omitting on `/health` and `/api/v1/public/*`.

### M4 — Malformed JSON body returns 500 instead of 400

**Surface:** Backend (live-confirmed) · error middleware
`POST /api/v1/public/contact` with bad JSON → `500 INTERNAL_ERROR` (no stack leak — body is generic). Incorrect client-error semantics; inflates error alerting.
**Fix:** Detect `err.type === 'entity.parse.failed'` / `SyntaxError` → return 400.

### M5 — Marketing site `kourti.com` is missing all security headers

**Surface:** Marketing (live-confirmed) · `marketing/vercel.json`
Response carries only HSTS — **no** CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, or `Permissions-Policy` (the file sets only `trailingSlash`/`cleanUrls`). The app's `vercel.json` has a full header block; marketing should match. Clickjacking + MIME-sniffing exposure on a site that hosts lead/contact forms.
**Fix:** Copy the app's `headers` block into `marketing/vercel.json` (CSP, XFO DENY, nosniff, Referrer-Policy, Permissions-Policy).

### M6 — Frontend CSRF module never fires for the real API (cross-origin)

**Surface:** Frontend · `src/lib/csrf.ts:184`, `src/lib/backendApi.ts`, `src/portal/portalApi.ts`
The fetch patch only injects `X-CSRF-Token` for same-origin URLs, but all API calls go to the cross-origin `VITE_BACKEND_API_URL` — so no CSRF token is ever sent. Staff bearer-in-header auth isn't CSRF-vulnerable, but this is dead code creating false assurance; the portal's `localStorage` tokens (H5) need explicit attention.
**Fix:** Remove dead CSRF code or wire it correctly; confirm backend enforces bearer-only on state-changing routes.

### M7 — Reset/invite tokens captured in client logs and `localStorage`

**Surface:** Frontend · `src/lib/logger.ts:105,22-23,116`, `src/App.tsx:490`
`logger` records full `window.location.href` (incl. `?token=…` reset/invite tokens) and persists logs to `localStorage` in all non-production modes (incl. staging). `window.history.replaceState` strips the token only _after_ initial render.
**Fix:** Strip sensitive query params (`token`, `code`, `email`, `state`) before logging; disable `localStorage` log persistence on all deployed envs; gate `window.__KOURTI_LOGS__` to localhost.

### M8 — Microsoft Clarity not stopped on cookie rejection (GDPR/NDPR)

**Surface:** Frontend · `src/components/CookieConsent.tsx:33-37`
On reject, Mixpanel opts out but Clarity is never halted (`window.clarity('consent', false)` / `('stop')` missing) — session recording continues without consent. Compliance gap given the consent ledger work.
**Fix:** Halt Clarity on reject; don't load its script until consent is granted.

### M9 — Missing rate limits on unauthenticated/auth-adjacent endpoints

**Surface:** Backend · unsubscribe `public.ts:156-175`; `/plans` `public.ts:80-129` (also uncached 4-table JOIN); reset-confirm `authRoutes.ts:682`, `portal.ts:185`
These lack `enforceRateLimit` (others have it). DB-write DoS / CPU (bcrypt) amplification, compounded by H3.
**Fix:** Add `enforceRateLimit` to each; add a 60s in-process cache for `/plans`.

### M10 — Rate limiter fails open permanently on first DB error

**Surface:** Backend · `src/lib/rateLimit.ts:118-129`
First DB error flips `useDbStore=false` for the process lifetime → per-process in-memory limits only (no cross-replica coordination), silently, with a single `console.warn`. A brief DB blip permanently degrades distributed limiting.
**Fix:** Retry DB store after a cooldown instead of disabling permanently; alert on the warn.

### M11 — `MARKETING_KB_URL` fetch: no SSRF allowlist, no size cap

**Surface:** Backend · `config/env.ts:58-60`, `services/marketingKb.ts`, `agents/marketingKbSync.ts`
Nightly KB sync fetches an env-configured URL validated only as a generic URL (accepts `169.254.169.254`, `localhost`, internal IPs) with no response-size cap. Operator-controlled today, but a compromised env or misconfig → SSRF / KB poisoning / heap exhaustion.
**Fix:** Allowlist host (`*.kourti.com`/`*.vercel.app`), reject private/link-local IPs, cap response bytes.

## LOW / INFO

- **Crypto key reuse (Low):** `JWT_SECRET` doubles as the HMAC key for signed file URLs (`storage.ts:422,461`), MFA-pending tokens (`jwt.ts:315`), and unsubscribe tokens (`consent.ts:157`). A single leak widens blast radius; rotating it breaks live unsubscribe links. → Introduce dedicated `SIGNED_URL_SECRET` / `UNSUBSCRIBE_HMAC_SECRET` (HKDF-derived).
- **`fieldCrypto` KDF (Low):** key derived via single-pass `SHA-256` rather than HKDF/scrypt (`fieldCrypto.ts:22`). Acceptable with a ≥32-char random key; prefer `crypto.hkdfSync`.
- **CSP `'unsafe-inline'` for scripts (Low):** app CSP and marketing `nginx.conf.template:13` allow inline scripts, weakening XSS backstop. → nonce/hash-based CSP.
- **Frontend injection sinks (Low–Med, precondition: malicious backend response):** unvalidated server URLs used for `window.location.href` in billing/calendar dialogs (`SeatCheckoutDialog.tsx:98`, `AddSeatsDialog.tsx:66`, `TrialExpiredModal.tsx:147`, `CalendarConnectDialog.tsx:32`); unvalidated `downloadUrl` as `<a href>` (`PortalMatterDetail.tsx:507`); `sanitize.ts` permissive `ALLOWED_URI_REGEXP` + `rel="noopener"` not forced; chart `color` CSS injection via `dangerouslySetInnerHTML` (`chart.tsx:78-98`); open-redirect via `location.state.from` post-login (`Auth.tsx:86`, `PortalLogin.tsx:34`). All require either a compromised backend or pre-existing XSS — fix as defense-in-depth (validate origins/paths/colors, force `rel`, cap to `https:`).
- **Impersonation token rendered in DOM (Low–Med):** `ImpersonationTab.tsx:104` shows the full impersonation token in a `<code>` element (and React DevTools state). → mask / write-only clipboard, clear from state.
- **`SELECT p.*` in session (Low):** `authRoutes.ts:698` returns the whole `profiles` row. → explicit column projection.
- **`morgan('combined')` logs full URLs incl. signed-URL `sig` (Low):** `app.ts:174`. → redact `sig`/`token`/`key` query params; also mount before `enforceHttps` if HTTP probes should be logged.
- **Direct `console.*` bypassing log gate (Low):** `ForgotPassword.tsx:61`, `SetPassword.tsx:58`, `ProfileTab.tsx:78`.
- **`SSO_SECRET_KEY` default constant (Low):** `env.ts:68` — prod boot-check guards it, but a staging env with `NODE_ENV≠production` would boot on the public default. → run the check whenever `NODE_ENV≠development`.
- **Dev-dependency CVEs (Low):** 6 moderate (`ws` uninitialized-memory via `@remotion/*`) — **dev-only**, not in the production bundle; `esbuild`/Vite dev-server CORS in marketing devDeps. → upgrade when convenient.
- **HSTS lacks `preload` (Info):** appropriate to skip on the shared `*.up.railway.app` domain; add `preload` only on owned apex domains.
- **`Permissions-Policy` absent on API (Info):** low value for a JSON API; trivially addable via Helmet.
- **Broad `Access-Control-Allow-Methods` (Info):** advertises full CRUD verb set (cors default); cosmetic.

## Confirmed secure (validated, no action)

**Live (production backend):** TLS 1.3 only, TLS 1.0/1.1 refused, valid LE cert; HTTP→HTTPS 301; full Helmet header set (HSTS, CSP, nosniff, XFO SAMEORIGIN, Referrer-Policy no-referrer, COOP/CORP same-origin); `X-Powered-By` suppressed; `alg:none`/forged JWT rejected (401); all authenticated + portal endpoints 401/403 unauthenticated (no data leak); CORS refuses to reflect untrusted origins; TRACE disabled; 14 sensitive paths (`.env`, `.git/config`, `package.json`, `metrics`, `swagger`, etc.) all return identical generic 404 — zero info disclosure.

**Code:** JWT `algorithms:['HS256']` pinned; token*version revocation on every sensitive auth event; bcrypt cost 12 + timing-safe dummy hash for user-enumeration resistance; staff multi-tenant `organization_id` scoping consistent across cases/documents/clients/contracts/invoices; Paystack webhook raw-body HMAC-SHA512 + `timingSafeEqual` + API re-verify; Multer MIME allowlist + ClamAV fail-closed in prod + sanitized filenames + org-ID path prefix; dev-seed neutralized at every prod boot; `AUTH_MODE=development` blocked in prod; staff/portal auth realms cryptographically isolated (`typ` claim cross-rejection); staff refresh-token reuse detection; staff access token in-memory + httpOnly refresh cookie; all content `dangerouslySetInnerHTML` routed through `sanitizeHTML()`; no `VITE*` secret keys in the client bundle; analytics PII sanitizer strips email/name/phone; production source maps disabled.

**Supply chain:** frontend + backend **production** dependencies — 0 known vulnerabilities. `.env` files gitignored and never in git history.
